# Karachur Bot

## О боте
Karachur Bot — Telegram-бот для групповых чатов с интеграцией Google Gemini AI. Один запущенный бот обслуживает сколько угодно чатов, и у каждого своя история, свой пул ключей Gemini и своя модель. Бот обрабатывает сообщения и файлы, сохраняет контекст переписки в SQLite и генерирует ответы с помощью моделей Gemini (мультимодальная поддержка). Поддерживает базовое форматирование Markdown → Telegram HTML (безопасная конвертация через markdown_converter.py) и режет длинные ответы по лимиту Telegram, не ломая теги (html_splitter.py).

## Функциональность

- 🤖 Ответы на сообщения, начинающиеся с триггерного слова "Карачур"
- 💬 Несколько чатов сразу: у каждого своя история, свои ключи и своя модель
- 🔑 Пул ключей Gemini на чат с автоматической ротацией при исчерпании дневной квоты
- 🎛 Выбор модели командой, отдельно для каждого чата
- 💭 Контекст: учитывается вся сохранённая история чата (см. раздел про БД)
- ↩️ Ответы и цитаты: бот видит, какому сообщению и какому выделенному в нём фрагменту отвечает реплика
- 🗜 Автоматическое сжатие контекста: когда история перерастает лимит токенов, её старая часть заменяется пересказом
- 📸 Поддержка медиа:
  - Изображения (JPEG, PNG, GIF, WebP)
  - Видео (MP4, WebM — до 20 МБ)
  - Документы (PDF и другие)
  - Аудио / голос / video note
  - Стикеры
- 🎙 Расшифровка голосовых сообщений — без триггерного слова, по факту присланного голосового
- 🧠 Мультимодальные запросы к Gemini (текст + медиа)
- ⏳ Заглушка "Генерирую ответ...", которую бот заменяет готовым текстом
- 🔁 Повторные попытки при сбоях Gemini (до 15 раз с растущей паузой)
- ✂️ Разбиение длинного ответа на части без разрыва HTML-тегов
- 💾 Локальное хранение истории (SQLite)
- 🔄 Автозагрузка и сохранение медиа
- 🧹 Нормализация Markdown в допустимый Telegram HTML (теги b, i, u, s, code, pre, a, tg-spoiler, br)
- ⚙️ Гибкая настройка через config.cfg
- 🛡 Безопасная фильтрация HTML (удаление лишних атрибутов)
- 🗃 Возможность последующей аналитики истории (простые SQL-запросы)

## Установка и настройка

### Предварительные требования
- Python 3.10+ (рекомендуется 3.12+)
- ffmpeg — всё скачанное медиа перекодируется им перед отправкой модели (см. «Перекодирование медиа»). Без него бот работает, но отдаёт файлы как есть: `apt install ffmpeg`
- Telegram Bot Token ([@BotFather](https://t.me/BotFather))
- Google Gemini API Key ([Google AI Studio](https://makersuite.google.com/))
- Доступ в интернет для вызова Gemini API

### Шаги по установке

1. **Клонирование репозитория:**
   ```bash
   git clone https://github.com/yourusername/karachur-bot.git
   cd karachur-bot
   ```

2. **Создание и активация виртуального окружения:**

   Windows:
   ```bash
   python -m venv venv
   venv\Scripts\activate
   ```

   Linux/Mac:
   ```bash
   python -m venv venv
   source venv/bin/activate
   ```

3. **Установка зависимостей:**
   ```bash
   pip install -r requirements.txt
   ```
   > Используются зависимости (ключевые):
   > - python-telegram-bot>=21.0.0
   > - google-genai>=0.7.0
   > - python-dotenv>=1.0.0 (при желании можно вынести ключи в .env)
   > - markdown==3.6 (конвертация форматирования)
   > - beautifulsoup4==4.12.3 (очистка/фильтрация HTML)

4. **Настройка конфигурации:**
   ```bash
   cp config.cfg.example config.cfg
   ```
   Затем отредактируйте `config.cfg`:
   ```ini
   [SETTINGS]
   BOT_TOKEN = YOUR_BOT_TOKEN_HERE
   GEMINI_API_KEY = YOUR_GEMINI_API_KEY_HERE
   DB_FILE = messages.db
   MEDIA_DIR = media
   TRIGGER_WORD = Карачур
   MODEL = gemini-2.5-flash-lite
   MAX_CONTEXT_TOKENS = 200000
   KEY_RPD_LIMIT = 250
   SYSTEM_PROMPT = [System prompt] Все сообщения до этого являются контекстом...
   ```
   Примечания:
   - MODEL — модель по умолчанию для новых чатов; каждый чат меняет её командой `/model` (см. «Выбор модели»)
   - GEMINI_API_KEY необязателен: это общий ключ на все чаты, и его можно оставить пустым, раздав ключи чатам командой `/addkey` (см. «Ключи Gemini»)
   - SYSTEM_PROMPT влияет на стиль ответов; полезно описать в нём служебные пометки, которые бот ставит перед репликами (см. разделы «Ответы и цитаты» и «Пересланные сообщения»)
   - При изменении MODEL убедитесь, что она доступна в регионе API

5. **Создание директории для медиафайлов:**
   ```bash
   mkdir -p media
   ```

6. **Запуск бота:**
   ```bash
   python bot.py
   ```

## Настройки конфигурации

### Основные параметры

- `BOT_TOKEN` — токен Telegram бота
- `GEMINI_API_KEY` — общий ключ Gemini, доступный всем чатам (необязательный: чат может работать на своих ключах)
- `DB_FILE` — файл базы данных
- `MEDIA_DIR` — директория для медиа
- `TRIGGER_WORD` — слово-триггер (регистр игнорируется)
- `MODEL` — модель Gemini по умолчанию, если чат не выбрал свою
- `SYSTEM_PROMPT` — системный промпт (включается перед историей)
- `MAX_CONTEXT_TOKENS` — потолок контекста в токенах, при превышении включается сжатие (по умолчанию 200000, параметр необязательный)
- `KEY_RPD_LIMIT` — после скольких запросов за сутки бот сам уводит ключ в конец очереди (по умолчанию 250, параметр необязательный; `0` отключает счётчик)

Дополнительно: можно вынести секреты в `.env` и загрузить их перед чтением конфига (необязательно).

## Использование

1. Добавьте бота в группу (желательно дать права администратора: для доступа к полному контенту, reply и удаления сообщения с ключом после `/addkey`).
2. Дайте чату ключ Gemini: `/addkey ВАШ_КЛЮЧ`. Если в `config.cfg` задан общий ключ, шаг можно пропустить — чат воспользуется им.
3. Напишите: `Карачур, что такое квантовая запутанность?` — триггер должен стоять в начале сообщения, регистр не важен.
4. Приложите изображение + подпись с триггером: бот учтёт визуальный контент.
5. Используйте базовое форматирование Markdown (жирный, курсив, код) — оно будет преобразовано в безопасный Telegram HTML.

Советы:
- Бот работает и в личке: групповой чат, супергруппа и приватный чат обрабатываются одинаково.
- Голосовое расшифровывается само, без триггера (см. раздел «Голосовые сообщения»).
- Один бот обслуживает сколько угодно чатов, и они друг о друге не знают (см. «Несколько чатов»).
- Длину контекста бот держит сам: старая часть истории сжимается в пересказ (см. раздел «Сжатие контекста»). БД при этом продолжает расти — сжатые сообщения из неё не удаляются.
- Для очистки истории можно вручную удалить/переименовать файл БД.

### Команды

| Команда | Что делает |
| --- | --- |
| `/keys` | Показывает ключи чата, их дневные счётчики и текущую модель |
| `/addkey КЛЮЧ` | Добавляет ключ Gemini в пул чата |
| `/delkey НОМЕР\|ХВОСТ` | Убирает ключ из пула чата |
| `/rotatekey` | Принудительно переключает чат на следующий ключ |
| `/model` | Показывает текущую модель и список доступных |
| `/model ИМЯ` | Переключает чат на другую модель |
| `/model default` | Возвращает модель из `config.cfg` |
| `/help` | Справка по командам |

Команды доступны всем участникам чата, отдельного списка администраторов у бота нет. Сообщения с командами в историю не попадают — обработчик обычных сообщений их не видит.

Сообщение с `/addkey` бот удаляет сразу, чтобы ключ не остался висеть в чате. В группе для этого нужны права на удаление сообщений: без них ключ придётся стирать вручную, и в логах появится предупреждение. В ответах ключи всегда замаскированы (`AIzaSy…7f3K`) — по хвосту их можно опознать в `/keys` и назвать в `/delkey`.

## Основные компоненты

### Несколько чатов
Один запущенный бот обслуживает сколько угодно чатов, и они полностью изолированы: своя история, свой пересказ, свой пул ключей, своя модель. Ничего общего, кроме файла БД, директории медиа и системного промпта, у них нет.

Детали:
- Все выборки истории идут с `chat_id`: и контекст, и пересказы, и поиск сообщения, которому отвечает реплика. Ответ на сообщение из другого чата с тем же номером в пометку не попадёт.
- `message_id` в Telegram уникален только внутри чата, поэтому ограничение уникальности в `messages` стоит на паре `(chat_id, message_id)`. В прежней схеме уникальным был один `message_id`, и сообщение второго чата затирало чужое.
- Чаты обслуживаются параллельно (`concurrent_updates`), а внутри чата ответы идут строго по очереди под своим замком. Иначе один чат, застрявший в повторах на несколько минут, превращался бы в очередь для всех остальных.
- Входящие сообщения сохраняются в базу сразу, до очереди на ответ, — история не отстаёт, пока бот занят предыдущим запросом.

### Ключи Gemini
Ключи принадлежат чату: пул набирается командой `/addkey`, и бот сам переключается между ключами, когда очередной выбирает дневную квоту (RPD).

**Квота считается на пару «проект и модель», а не на ключ.** Это видно прямо в имени квоты, которое Gemini присылает в ошибке: `GenerateRequestsPerDayPer**ProjectPerModel**`. Поэтому счётчики и пометка «квота выбрана» живут в отдельной таблице `key_quota` с ключом `(key_id, model)`, а `/keys` показывает состояние по текущей модели чата. Пометить весь ключ было бы грубой ошибкой: у части моделей бесплатной квоты нет вовсе, и один запрос к такой модели выводил бы из строя весь пул чата до полуночи. Отказ по самому ключу (401, 403) от модели не зависит и остаётся в `api_keys`.

Как устроено хранение:
- Сам ключ лежит в базе один раз (`api_keys`), а привязка к чатам — отдельно (`chat_keys`). Квоту Google считает на проект, а не на чат: добавьте один ключ в два чата — счётчик у него всё равно останется общим, иначе бот решил бы, что квоты вдвое больше.
- `GEMINI_API_KEY` из `config.cfg` — общий ключ, доступный всем чатам сразу. Он живёт в базе на общих правах и в `/keys` помечен как общий; убрать его можно только из конфига. При запуске бот приводит базу в соответствие с конфигом: убрали ключ оттуда — отвяжется и здесь.
- Указатель на активный ключ лежит в базе, поэтому после перезапуска бот продолжает с того же ключа, а не начинает заново жечь первый по списку.
- Ключ, выпавший из всех чатов, удаляется вместе со счётчиками. Это же — способ вернуть в строй ключ, ошибочно помеченный битым: `/delkey`, затем `/addkey`.

Когда ключ выбывает:
- **Дневная квота на текущую модель выбрана** — до полуночи по тихоокеанскому времени, когда Google обнуляет счётчики. На других моделях этот же ключ продолжает работать. Счётчики сбрасываются лениво, при первом обращении в новые сутки.
- **Ключ отклонён API** (401, 403, а также `API key not valid` под кодом 400) — навсегда: сам такой ключ не починится. В `/keys` видно причину.

Как бот отличает дневной лимит от минутного: в деталях ошибки 429 Gemini называет нарушенную квоту (`GenerateRequestsPerDayPerProjectPerModel`). Если в названии есть «per day» — ключ выбыл до полуночи и надо брать следующий; если «per minute» — ключ живой, и бот просто ждёт паузу, которую API сам же и рекомендовал.

Про `KEY_RPD_LIMIT`: это собственный счётчик бота, страховка на случай, если формат ошибки поменяется. Он **не запрещает** работу — дневной лимит бесплатного тарифа зависит от модели, и настройка легко оказывается заниженной. Поэтому бот сначала обходит ключи по счётчику, а если по нему не годится ни один, пробует ещё раз, не глядя на него: пусть лучше откажет API, чем бот сам себе запретит работать при живой квоте.

Ротация при ответе происходит внутри цикла повторов и тратит попытку — так цикл не закружится на пуле из сотни мёртвых ключей. Медиа при смене ключа выгружается заново: выгрузка в Files API принадлежит проекту того ключа, которым её делали, и после ротации ссылка становится чужой. Поэтому запрос пересобирается под новый ключ целиком, а кэш выгруженных файлов ведётся по паре «ключ + файл».

Когда рабочих ключей не осталось, бот не сыплет трейсбеком, а пишет в чат, сколько ключей выбыло и почему, и когда обнулятся квоты.

### Выбор модели
Модель задаётся отдельно для каждого чата командой `/model`; `MODEL` из конфига остаётся значением по умолчанию для тех, кто свою не выбирал. `/model` без аргументов показывает текущую модель и список доступных активному ключу — он берётся у API, а не зашит в код. Имя проверяется по этому же списку, так что опечатка не пройдёт молча; если список получить не удалось (нет рабочего ключа, легло API), имя принимается как есть.

Смена модели на историю не влияет: контекст собирается из базы одинаково, меняется только адресат запроса. А вот квоты у каждой модели свои, и это важно на практике:

- После перехода на более тяжёлую модель ключи будут кончаться быстрее, чем говорит `KEY_RPD_LIMIT` — этот потолок один на все модели.
- **У части моделей из списка бесплатной квоты нет вообще.** Первый же запрос к такой отвечает 429 с дневной квотой, и бот перебирает весь пул за секунды. Ключи при этом не пострадают: помечается пара «ключ и модель», и достаточно вернуться на рабочую модель (`/model` или `/model default`), чтобы всё заработало сразу.
- Список от API включает и такие модели — он показывает всё, что доступно ключу, а не всё, что имеет смысл в чате. TTS, музыкальные, робототехнические и image-модели там тоже будут.

### База данных
- Таблица messages хранит:
  - message_id, chat_id, user_id, username
  - content (текст/подпись целиком, вместе с триггерным словом — без него реплика начиналась бы с запятой, а обращение, на которое отвечает бот, терялось)
  - media_type, mime_type, file_id, file_name
  - reply_to_message_id
  - quote_text (фрагмент, выделенный при ответе с цитированием)
  - forward_origin (настоящий автор пересланного сообщения)
  - is_bot (флаг собственного ответа)
  - summarized (сообщение уже вошло в пересказ и в контекст больше не подставляется)
  - media_path (где лежит файл после перекодирования; у старых записей пусто, тогда путь считается по mime)
  - Ограничение уникальности стоит на паре `(chat_id, message_id)`, индекс — на `(chat_id, summarized, timestamp)`
- Таблица context_summaries хранит пересказы сжатых кусков истории (chat_id, summary, covered_messages, created_at)
- Таблица api_keys хранит сами ключи и то, что не зависит от модели (api_key, broken_reason, added_at)
- Таблица key_quota хранит счётчики и квоты на пару `(key_id, model)` — quota_date, requests_today, daily_exhausted
- Таблица chat_keys связывает ключи с чатами (chat_id, key_id, position); `chat_id = 0` означает общий ключ из `config.cfg`
- Таблица chat_settings хранит настройки чата (model, active_key_id)
- Базы, созданные версиями бота без поддержки нескольких чатов, не открываются: в них истории всех чатов лежат вперемешку, а `message_id` уникален глобально. Бот падает с понятным сообщением — файл базы надо удалить или переименовать, новая создастся сама
- Возможные дальнейшие улучшения:
  - Очистка старых записей (ручная)

### Сжатие контекста
История растёт бесконечно, поэтому рано или поздно она перестаёт помещаться в модель. Перед каждым запросом бот прикидывает размер контекста и, если оценка подобралась к лимиту, уточняет его через `count_tokens`. Когда контекст перерастает `MAX_CONTEXT_TOKENS`:

1. Самая старая часть истории уходит модели на пересказ — с медиа, чтобы содержимое картинок и файлов не потерялось.
2. Пересказ ложится в `context_summaries`, а вошедшие в него сообщения помечаются `summarized = 1`.
3. Дальше в контекст идут пересказ плюс несжатые сообщения; каждый следующий пересказ вбирает в себя предыдущий.

Детали:
- Режем не половину наугад, а столько, чтобы остаток уложился примерно в половину лимита — иначе сжатие срабатывало бы почти на каждое сообщение.
- Последние `KEEP_RECENT_MESSAGES` (10) сообщений остаются дословно всегда.
- Один проход не всегда доводит до цели: пересказ тоже занимает место. Проходов за один ответ делается не больше `MAX_COMPRESSION_ROUNDS` (3), дальше запрос уходит как есть.
- Точный подсчёт токенов — лишний запрос к API, поэтому первый заход отсекается грубой оценкой (`CHARS_PER_TOKEN`, `MEDIA_TOKEN_ESTIMATE`); `count_tokens` зовётся, только если оценка перевалила за `TOKEN_CHECK_RATIO` от лимита.
- Сообщения из `messages` не удаляются — история остаётся доступной для SQL-запросов.
- Сжатие не критично для ответа: если посчитать токены или получить пересказ не вышло, запрос уходит как есть.
- Чтобы начать контекст с нуля, достаточно очистить `context_summaries` и сбросить флаг: `UPDATE messages SET summarized = 0;`

### Ответы и цитаты
В плоской истории реплика-ответ оторвана от своего адресата: между ними может лежать сколько угодно чужих сообщений, а сам адресат — уже уйти в пересказ. Поэтому перед текстом такой реплики в контекст уходит служебная пометка:

```
[В ответ на сообщение "Вася aka vasya date:2026-08-03 12:00:00+00:00": «Кто пойдёт в поход?»]
[Петя aka petya date:2026-08-03 12:05:00+00:00]: я пойду
```

Детали:
- Адресат ищется по всей таблице `messages`, а не только по несжатой части: ответить могут и на сообщение, давно ушедшее в пересказ. Если сообщения в базе нет (оно старше бота), в пометку идёт `[В ответ на сообщение, которого нет в истории]`.
- Ответ боту помечается как `[В ответ на сообщение бота: «...»]`.
- Текст адресата сжимается в одну строку и режется до `REPLY_SNIPPET_LIMIT` (300 символов) — пометка должна дать его опознать, а не размножить популярное сообщение по всему контексту. Вложение отмечается как `[вложение: photo]`.
- Если отвечающий выделил кусок текста, к пометке добавляется `Процитирован фрагмент: «...»`. Цитата приезжает и без `reply_to_message_id` — так Telegram присылает цитаты из других чатов, и тогда пометка состоит из неё одной.
- Собственные ответы бота пометки не получают: реплики роли `model` уходят вообще без служебной разметки, иначе модель тащит её в начало новых ответов. На случай, если она всё же скопирует пометку из чужой реплики, `strip_service_prefixes` срезает её вместе с пометкой автора.

### Пересланные сообщения
Пересланное сообщение приходит от того, кто нажал «переслать»: в `from_user` стоит он, а в `text` лежат чужие слова. Без пометки модель припишет их переславшему. Настоящий автор лежит в `forward_origin`, и перед текстом такой реплики уходит:

```
[Переслано от "Вася aka vasya date:2026-07-01 09:30:00+00:00"]
[Петя aka petya date:2026-08-03 12:05:00+00:00]: смотрите что нашёл
```

Детали:
- Время в пометке — это время оригинала из `forward_origin.date`; в `date:` самой реплики стоит момент пересылки.
- Четыре вида источника: обычный пользователь (`от "..."`), закрывший ссылку на аккаунт (`от скрытого пользователя "..."` — остаётся одно имя без ника), чат (`из чата "..."`) и канал (`из канала "..."`). У чатов и каналов подпись автора поста добавляется как `, подпись автора: ...`. Если Telegram заведёт новый вид источника, в пометку идёт `из неизвестного источника (date:...)` — сказать про сам факт пересылки полезнее, чем отдать чужие слова за слова переславшего.
- Если отвечают на пересланное, это видно и в пометке адресата: `[В ответ на сообщение "Петя aka petya date:..." (переслано от "Вася aka vasya date:..."): «...»]`.
- Пометка о пересылке идёт первой, перед пометками об ответе и цитате, и живёт с ними в одних скобках.

### Обработка медиафайлов
- Файлы сохраняются по file_id (или имени документа)
- MIME → расширение определяется через карту
- Ограничение Telegram по размеру (видео до ~20 МБ)
- Рекомендуется следить за размером директории media/

### Перекодирование медиа
Telegram отдаёт файлы такими, какими их собрал отправитель, и среди них попадаются контейнеры, на которых модель спотыкается. Реальный случай: видео-стикер, у которого в контейнере записано 33 мс, а в видеодорожке — 6 секунд. Файл читается любым плеером, загружается в Files API и переходит в ACTIVE, а `generateContent` отвечает на него `400 Request contains an invalid argument` — без единого намёка, что не так. Такое вложение остаётся в истории и валит каждый следующий запрос, включая запрос на сжатие, то есть само оттуда уже не уедет.

Отличить такой файл заранее нечем — битым бывает не формат, а конкретный файл. Поэтому всё медиа сразу после скачивания проходит через ffmpeg: он читает исходник своим разбором и пишет заново, с согласованными заголовками. Заодно пёстрый набор форматов сводится к короткому списку тех, что Gemini принимает наверняка.

| Что пришло | Во что переводится |
| --- | --- |
| видео любого вида, gif | mp4 (H.264 + AAC) |
| аудио, голосовые | ogg (переливкой, без пересжатия речи) |
| webp, heic, heif | png |
| jpeg, png | остаются как есть |
| pdf, текст, документы | не трогаются |

Детали:
- **Голосовые не пересжимаются.** Telegram присылает opus в ogg, Gemini этот формат принимает, поэтому дорожка просто переливается в новый контейнер (`-c:a copy`): заголовки пересобираются, а звук остаётся ровно тем же. Расшифровка речи от второго сжатия только теряла бы. Если переливка не проходит (wav, mp3 — в ogg они не укладываются), файл пережимается в opus.
- **Фотографии не трогаются.** Telegram отдаёт их как `image/jpeg`, под правила они не попадают. Из картинок перекодируются только webp-стикеры и heic/heif.
- Даже mp4 пересобирается заново — именно так чинятся битые заголовки.
- Кадр приводится к чётным сторонам (`scale=trunc(iw/2)*2:...`): H.264 не кодирует нечётные, а Telegram присылает и 489×512.
- Путь готового файла пишется в `messages.media_path`: после ffmpeg у него другое расширение, и по mime его уже не вычислить. У записей, сделанных до появления перекодирования, колонка пуста — для них путь считается по-старому.
- Исходник после успешной перекодировки удаляется, результат пишется через временный файл — неудача ffmpeg оставляет всё как было.
- Если ffmpeg не установлен или не справился, файл уходит модели как есть: перекодирование повышает шансы, но не должно ломать работу бота.

### Голосовые сообщения
Голосовое бот расшифровывает сам, без триггерного слова: в контекст такого запроса уходит одно-единственное сообщение — само голосовое с припиской «Напиши расшифровку голосового сообщения». Ни история, ни пересказ туда не идут: расшифровке чужой разговор не нужен, а лишний контекст только провоцирует модель отвечать на него вместо расшифровки.

Если в подписи к голосовому стоит триггер, работает обычный путь — полный контекст и обычный ответ.

### Отправка ответа
Ответ модели приходит не мгновенно, поэтому бот сразу отвечает заглушкой `⏳ Генерирую ответ...` и потом подменяет её текстом:

1. Заглушка уходит ответом на сообщение пользователя. Не отправилась — не беда, дальше просто шлётся обычный ответ.
2. Готовый текст конвертируется в Telegram HTML и режется `split_html_message` на куски по 3900 символов — с закрытием и восстановлением открытых тегов на границе.
3. Первый кусок заменяет заглушку, остальные уходят отдельными ответами. Если кусков больше четырёх, между отправками делается пауза в 10 секунд, чтобы не упереться в лимиты Telegram.
4. Отредактировать заглушку не вышло (её удалили, истёк срок правки) — бот убирает её и отвечает обычным сообщением.

Ошибки:
- В чат уходит полный текст ошибки вместе с числом потраченных попыток — по нему понятно, что случилось.
- В контекст модели вместо этой простыни кладётся короткая пометка `ошибка gemini api`, и только один раз: незачем учить модель отвечать чужими трейсбеками.

### Повторные попытки
Gemini регулярно отвечает 429, 500 или просто пустым текстом, поэтому каждый запрос к модели (и ответ в чат, и пересказ истории) идёт через `generate_with_retries`: до `MAX_RETRIES` (15) попыток, суммарно около 18 минут ожидания.

Что бот делает с ошибкой, зависит от того, чья это беда — запроса, сети или ключа (`classify_api_error`):

| Ошибка | Что это | Что делает бот |
| --- | --- | --- |
| 429 с квотой «per day» | Дневная квота ключа выбрана | Помечает ключ и без паузы берёт следующий |
| 429 с квотой «per minute» | Частим, ключ живой | Ждёт `retryDelay` и повторяет тем же ключом |
| 401, 403, `API key not valid` | Ключ отклонён | Помечает ключ битым и берёт следующий |
| 400, 404 | Кривой запрос или нет такой модели | Сдаётся сразу: само не пройдёт |
| 500, таймаут, обрыв связи | Временное | Повторяет с растущей паузой |

Детали:
- Пауза растёт экспоненциально от `RETRY_BASE_DELAY` (2 с) до `RETRY_MAX_DELAY` (120 с), плюс джиттер — чтобы повторы не выстраивались в ровную сетку.
- Если в ошибке 429 пришёл рекомендованный `retryDelay`, слушаемся его, а не своей формулы.
- Смена ключа паузы не требует — ждать нечего, следующий виток пойдёт другим ключом. Попытку она при этом тратит.
- Запрос, заблокированный фильтрами безопасности, не повторяется: блокировка детерминирована. А вот пустой ответ модели повторить стоит, это обычно временное.
- Вызов синхронный, поэтому уходит в отдельный поток: event loop бота на время ожидания не замирает. Туда же уходит и сборка запроса — она выгружает медиа и тоже ходит в сеть.

### Интеграция с Gemini AI
- Клиент создаётся через `genai.Client(api_key=...)` — свой на каждый ключ пула
- Формируется список контента (SYSTEM_PROMPT + пересказ сжатой истории + разговор)
- Чужие реплики уходят с пометкой автора `[Имя aka ник date:...]: ` и, если это ответ, с пометкой об адресате (см. раздел «Ответы и цитаты»); свои — без пометок вообще: роль `model` и так говорит, чьи они, а с пометкой модель копировала её в начало новых ответов
- Запрос всегда заканчивается репликой роли `user`: на запрос, который заканчивается репликой роли `model`, Gemini отвечает ошибкой 400 «Requests ending with a model turn are not supported»
- Возможности расширения:
  - Потоковые ответы (stream)
  - Взвешивание медиа частей

## Решение проблем

### Частые ошибки

1. **Файл конфигурации отсутствует**
   - Создайте из примера: `cp config.cfg.example config.cfg`
2. **Неверный токен/ключ**
   - Перепроверьте значения без пробелов/кавычек
   - Ключ, отклонённый API, виден в `/keys` вместе с причиной. Вернуть его в строй после починки: `/delkey`, затем `/addkey`
3. **Rate limit Gemini**
   - Бот повторяет запрос сам (см. «Повторные попытки»), в логах это видно как «Повтор через N с.»
   - Если попытки кончились, помогает модель попроще или меньший `MAX_CONTEXT_TOKENS`
4. **«Ни один из N ключей чата не работает с моделью …»**
   - Сначала посмотрите на саму модель: у части моделей бесплатной квоты нет, и тогда об неё спотыкаются сразу все ключи. Вернитесь на рабочую — `/model default` — и всё заработает немедленно, ключи от этого не страдают
   - Если модель точно рабочая, пул действительно исчерпан: `/keys` покажет, у кого кончилась квота, а кто отклонён API. Добавьте ещё ключ (`/addkey`) или дождитесь обнуления — время сброса бот называет в том же сообщении
5. **База не открывается: «сделана версией бота без поддержки нескольких чатов»**
   - Схема изменилась несовместимо (см. «База данных»). Удалите или переименуйте файл БД — новая создастся сама
6. **Нет реакции на триггер**
   - Триггер должен стоять в начале сообщения или подписи: `Карачур, привет` сработает, а `Привет, Карачур` — нет
   - Регистр не важен, а вот пробелы и опечатки в слове — важны
7. **Файлы не сохраняются**
   - Проверьте права на директорию media/
8. **Ключ остался висеть в чате после `/addkey`**
   - Боту не хватило прав на удаление сообщений: выдайте их или сотрите сообщение вручную. В логах это видно как «Не удалось удалить сообщение с ключом»
9. **Unicode ошибки в Windows консоли**
   - Запустите: `chcp 65001` перед запуском

### Логирование
- Логи выводятся в stdout
- Для отладки: временно смените уровень:
  ```python
  logging.basicConfig(level=logging.DEBUG)
  ```
- Можно перенаправить в файл: `python bot.py > bot.log 2>&1`
- По логам видно основное: сжатие контекста («Контекст: N токенов из M»), повторы («Попытка N из 15 не удалась»), ротацию ключей («Чат X переключился на ключ …») и сохранение сообщений
- Ключи в логах замаскированы так же, как в чате

## Тесты

```bash
pip install -r requirements-dev.txt
pytest
```

Тесты не ходят в сеть и не требуют ни `config.cfg`, ни ключей: на чистой машине со свежим клоном они проходят как есть. Клиент Gemini подменяется подделкой, которая отвечает по заранее заданному сценарию, Telegram — парой объектов, запоминающих отправленное, а база заводится своя на каждый тест во временной директории.

Как это устроено:
- `conftest.py` в корне готовит тестовый конфиг во временной директории и передаёт путь через `KARACHUR_CONFIG` — до того, как pytest доберётся до самих тестов: `bot.py` читает конфиг на импорте. Ту же переменную можно использовать и при запуске бота, если конфиг лежит не рядом с ним.
- Фикстура `gemini` подменяет `api_keys.client_for_key` и укорачивает паузы между попытками, иначе сценарий с повторами шёл бы минутами.
- Фикстура `run_command` зовёт обработчики команд на поддельном контексте и отдаёт то, что бот ответил бы в чат.

Что покрыто:

| Файл | О чём |
| --- | --- |
| `tests/test_context.py` | Разделение истории по чатам, адресаты ответов, пересказы, отказ от старой схемы БД |
| `tests/test_key_pool.py` | Владение ключами, общий счётчик, выбытие по квоте и по отказу API, ротация, разбор ошибок |
| `tests/test_retries.py` | Цикл повторов: смена ключа, пересборка запроса, ожидание на минутном лимите, сжатие контекста |
| `tests/test_commands.py` | Команды глазами человека в чате, включая удаление сообщения с ключом и маскировку |
| `tests/test_startup.py` | Запуск: регистрация команд, создание таблиц, привязка общего ключа |
| `tests/test_media.py` | Перекодирование: правила форматов и настоящие прогоны ffmpeg |

В CI (`.github/workflows/tests.yml`) тесты гоняются на Python 3.10–3.13 при каждом push. Соседний `pylint.yml` проверяет линтером все файлы репозитория, включая тесты, поэтому новые тесты тоже должны быть чистыми: для фикстур и подделок в них стоят точечные `# pylint: disable`.
